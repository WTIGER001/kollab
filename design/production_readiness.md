# Production readiness hardening

The implementation hardening and local verification are recorded below. Local qualification includes the selected bidirectional sync and multi-instance operating model. External-service checks remain deployment-specific. Azure backup and Jira remain intentional prototypes. Other advertised features are being checked against their implementation and integration paths; passing a bundle build alone is not release qualification.

The baseline review found document collection authorization gaps, WebSocket write authorization gaps, unscoped administrative archive operations, incomplete database restore and sync import, incomplete route wiring, local session propagation failures, and missing release checks. Baseline frontend verification passed 103 tests in 22 files and built a production bundle. The actual TypeScript project check reported 368 diagnostics; the documented root `tsc --noEmit` checked no application files. Backend integration tests ran against disposable PostgreSQL and failed an authentication configuration expectation. The validation results after fixes are recorded below.

Authorization uses the same document evaluator for lists and direct reads. Slugs and aliases resolve before ancestry evaluation. Versions are confined to their document. Non-document resources use explicit scope checks; administrative backup and sync operations require server administration. WebSocket connections remain bound to the document authorized at connection time, recheck access before delivery and updates, and reject write updates from readers. Local sessions are checked against the current active user and a credential fingerprint so deleting, disabling, or changing the password invalidates old credentials.

Destination validation binds a parent, project, and team to one real space and requires write access before creating or moving content. Personal spaces receive an owner role. HTTP headers have bounded read time, requests have size limits, and request logging redacts browser attachment credentials as well as WebSocket tokens.

See [the user-facing readiness notes](../user_guide/production_readiness.md). This document records the verified scope and remaining release gates.

## Implemented boundaries and behavior

- **Authentication:** disabled OIDC identities are rejected after provisioning and on WebSocket checks. Local JWTs carry a password-hash fingerprint, checked against the current active database user on every request and WebSocket authorization. The SPA uses one session context for local and OIDC accounts. `/api/me` returns the current identity and administrator status. Configuration failures show a retry page instead of pretending first-run setup is available.
- **Authorization:** document lists, hierarchical exports, versions, and derived collections respect page access. Team/project creation and moves validate the destination. Delete and grant actions require the corresponding containing-space permission. Integration credentials are usable only within their authorized scope. Theme and system operations require administration. `/api/documents/{id}/capabilities` controls editing affordances.
- **Media:** `0011_image_ownership.sql` adds uploader ownership. Private images require an authorized owner, library, or page reader; configured site branding is public. Rendering URLs add credentials only for Kollab's media endpoints. Raster uploads validate decoded format and dimensions before allocation (40 megapixels, 10 MB); passive SVG drawing elements are allowed while scripts, external references, events, and directives are rejected. Local storage uses `os.Root` and atomic writes to constrain paths and avoid partially written files. Macro markup uses DOMPurify; document preview frames are sandboxed.
- **Archive recovery:** `kollab.database.v2` snapshots include all public application tables, permission records, attachments, version history, and the migration ledger. Restore validates table completeness and migration checksums, then uses one PostgreSQL transaction with sequence repair. ZIP paths and expanded size are checked before installation. Staging occurs inside the uploads mount; per-entry renames preserve the mount itself. Database failure rolls files back. Failed filesystem rollback preserves its recovery directory and reports an administrator recovery requirement. Local and PostgreSQL maintenance gates exclude ordinary HTTP requests, collaboration mutations, and scheduled cleanup across replicas while exporting/restoring. Archive restoration disconnects editors with a reload signal so pre-restore CRDT state is discarded. An interrupted file operation leaves a recovery marker that fences further workspace operations. Replica invalidation commits atomically with restored database state.
- **Offline synchronization:** all primary-key application tables receive tracking triggers after permission-schema initialization. Imports apply ordered upserts/deletes transactionally with outbound tracking suppressed. Packages require an HMAC SHA-256 signature using an operator-provided `SYNC_SIGNING_KEY` of at least 32 bytes. A common key and compatible migration ledger are required between installations. The supported format is `kollab.sync.v3`; legacy sync packages are rejected. Per-installation vector clocks, portable permission identities, explicit conflict review, tombstones, and retained losing versions support both directions. See [the synchronization design](multi_instance_sync.md).
- **Collaboration:** `0012_collaborative_state.sql` stores a bounded full Yjs state per page. `0013_collaborative_projection.sql` adds the readable JSON committed atomically with each accepted revision. The browser derives this JSON from the same Yjs fragment, and document reads, keyword search, exports, sharing, and image-access checks prefer it over delayed REST saves. Clients send revisioned snapshots; PostgreSQL compare-and-swap rejects stale writes and returns the current state for client-side CRDT merging. Acknowledgments identify the accepted update, and changes made while an acknowledgment is outstanding are sent afterward. Reconnect merges local state with persisted state. The content editor waits for synchronization before enabling editing, avoiding duplicate CRDT initialization from a stale JSON copy. REST saves remain serialized, pending content survives component teardown, and the browser warns before leaving with a pending save. Version restoration atomically saves a recovery snapshot, restores JSON, and invalidates the prior CRDT state, then disconnects that page's clients for reload. Queued messages from detached clients are ignored. PostgreSQL polling shares accepted snapshots, presence, cursors, and restoration epochs across API replicas. Docker Compose defaults to two replicas with a shared uploads mount; the tested concurrency target is five editors.
- **Sharing:** `/share/{token}` resolves through `POST /api/shared-links/open`, keeping the raw link token out of API request URLs. Password and expiry checks apply. Anonymous visitors can read; comment/edit actions require a signed-in identity. Authenticated API calls carry page-scoped sharing headers; WebSocket sharing credentials use a subprotocol field and are rechecked on updates/delivery. Only viewer, commenter, and editor sharing roles can be created. Public scope accepts the existing `anyone` payload and `anonymous` alias. Shared media uses signed one-hour page capabilities; each image/attachment request rechecks link expiry/revocation.
- **Integrations and exports:** GitLab single-issue cards call the configured GitLab provider rather than returning sample issues. Issue lists traverse project/group pagination with a 30-second deadline and 100-page limit; failure is explicit rather than returning a misleading partial list. Credential-bearing redirects cannot change origin. The internal Confluence fetch service requests actual page content and metadata, but it is not wired to an operator-facing live embed flow. Confluence archive import is the available user workflow. Export excludes restricted descendants, constrains network image downloads, and reports PDF failures explicitly. The backend image includes Chromium and fonts; PDF rendering has a timeout, concurrency limit, disabled scripting, and blocked external resource requests.
- **Delivery:** production startup requires a persistent database URL. Disposable automatic databases require explicit `DEV_DATABASE=true`. Vite API and WebSocket traffic defaults to the same origin. Docker publishes the edge proxy rather than conflicting backend/proxy host ports. Frontend builds perform the actual TypeScript project build; CI runs frontend tests/lint/build and the full Go suite with >60% coverage before deployment.

- **Empty states and themes:** repository collection responses use empty arrays. Automatically generated team/project portal content uses JSON serialization so punctuation and control characters in names cannot corrupt its document payload. Personal settings handle empty pages, image libraries resolve abbreviated routes to persisted IDs, and load failures are visible. Preset choices persist in browser storage; saved workspace colors apply to the Default preset. Primary button foregrounds are selected for contrast and injected through `--primary-contrast`.

## Verification status

The complete Go suite passed with **63.9% statement coverage**, including disposable PostgreSQL integration tests. Collaboration, document, storage, multi-replica coordination, synchronization, and maintenance race checks passed. The frontend TypeScript project build and production bundling passed. All **113 frontend tests in 25 files** passed. ESLint completed with **0 errors and 318 warnings**; these warnings remain technical debt and are not evidence of complete production qualification. A dry-run offline `npm ci` validated lockfile consistency.

Real-browser checks used an isolated API, Vite process, disposable PostgreSQL container, and synthetic account. Verified login/session recovery, editing and reloading, content persistence through API restart, password-protected anonymous sharing, link revocation, empty personal settings, task/notification/trash empty states, abbreviated image-library routes, and document readability in light/dark Default, Workbench, Editorial, and Neobrutal presets. These are bounded workflow checks, not a claim that every macro or external provider was exercised.

The initial entry bundle was reduced from approximately 1.3 MB gzip to 283 KB gzip by deferring editor routes. The editor itself remains large (approximately 1 MB gzip), and the build reports large-chunk warnings. Existing lint warnings remain; errors are release-blocking in CI.

## Operating decisions and remaining deployment checks

The user selected bidirectional offline synchronization, multiple API instances, and 2–5 concurrent editors. Verification uses the local computer. No old backups or legacy sync compatibility are required. These decisions are implemented in [the synchronization design](multi_instance_sync.md).

The additional integration tests cover two installations exchanging updates and permissions, reviewed conflicts and reverse propagation, deletion tombstones, compact replication cursors, destination-only dependent records, two hubs with five editors, replica recovery, shared media credentials, distributed maintenance, and retained file versions. Frontend tests cover the conflict review flow and editor initialization/restore fencing. Two actual API processes started concurrently against an isolated database, and browser edits were observed in both directions through separate API endpoints. The Caddy configuration passed offline adaptation validation.

Real OIDC, GitLab, Confluence, AI/embedding, document conversion, and TLS deployment configuration still need qualification with the intended services and credentials. No production deployment or live provider mutation was requested. Azure backup and Jira remain excluded prototypes. Existing lint warnings and large editor chunks are recorded technical debt, not hidden by the passing checks.

No deployment, production data migration, or provider-side mutation was performed. The disposable verification processes, database container, and browser tabs were cleaned up after checks. Vector embeddings and derived task/property indexes are still refreshed through the normal save pipeline; keyword search and direct content reads use the durable projection. Version restore should be performed after editors save their work. All API replicas coordinate the operation and invalidate stale editor state.
